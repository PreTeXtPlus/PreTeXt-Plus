# Interactives, video and external exercises

Plan for robust support of content that comes from outside the document: PreTeXt's
`<interactive>` (GeoGebra, Desmos, CalcPlot3D, JSXGraph, …), `<video>` (YouTube and
local files), and exercises served by another system (WeBWorK, STACK, MyOpenMath).

**Status:** Phases 1 and 2 are done (2026-11-11): pretext-html 0.20.0 returns the iframe
pages and the live preview shows them, sandboxed. Phase 4 (Insert entries, pasting a link, lint) is done too, and MyOpenMath is checked.
Phase 3 is deferred by decision. What is left is WeBWorK (Phase 5) and static outputs
(Phase 6), neither of which starts in this repository.

## What the live preview did before Phase 2 (measured 2026-11-11)

The table is the starting point, kept for the rows later phases still owe. After Phase 2
the `@geogebra` and `@platform` rows work as described under Phase 2, and the YouTube
row has been seen loading its player in the real editor.

Found by rendering one document holding every kind through `@pretextbook/pretext-html`
0.19.1 and reading the HTML. Only the JSXGraph row has been watched working in a
browser; "should work" means the markup is right and nothing more.

| Element | What the preview emits | State |
| --- | --- | --- |
| `interactive` with `@desmos`, `@circuitjs`, `@iframe="https://…"` | an iframe straight to the service | should work |
| `interactive @calcplot3d` | an iframe to the service, but with no `@variant` the URL is only `?type=…` | works only with `@variant` |
| `interactive @geogebra`, and every `@platform` (geogebra, jsxgraph, d3, sage, doenetml, javascript) | `<iframe src="ID-if.html">`, a page that is never written | **broken** — Phase 1 and 2 |
| `interactive @iframe="local.html"` | `external/local.html` | broken — Phase 3 |
| `video @youtube` / `@vimeo` | an embed iframe | should work; see open questions |
| `video @source` | `<video src="external/clip.mp4">` | needs Phase 3 |
| `myopenmath` | an iframe to `embedq2.php` | should work |
| `stack` | an inert `<div data-qfile="external/q.xml">` | needs a STACK server and the question file |
| `webwork` | `PTX:ERROR could not load WeBWorK representation file`; a problem given only by `@source` renders empty | **broken** — Phase 5 |

Why the `@platform` rows are broken: PreTeXt's assembly rewrites `@geogebra` into the
`@platform` form, and every `@platform` interactive is framed from a second page that
`pretext-html.xsl` writes with `exsl:document` (`mode="create-iframe-page"`). The preview
stylesheet stubbed that template, because the WASM build has no filesystem and any
`exsl:document` aborts it.

Things that shape the rest of the plan:

- **The preview iframe is unsandboxed `srcdoc`, same origin as the editor.** The editor
  reads and patches its DOM directly. Nothing an author writes runs as script there
  today.
- **An interactive's page runs the author's JavaScript** (`<script>` and `@source`). In
  a shared project that is a collaborator's script. `docs/build-targets.md` moved
  published output to `pub.pretext.plus` for exactly this reason.
- **File assets are image-shaped.** `Content::AttachedFiles::CONTENT_TYPE_EXTENSIONS`
  knows only image types, so anything else is presented as a bare `ref` with no
  extension, and everything but SVG is served `disposition: :attachment`.
- **`external/:ref` is public and takes one path segment**, so `external/foo/bar.html`
  has nowhere to live.
- **Full builds are real PreTeXt** on the build server, so `@platform` interactives
  already work in a published website. The build server reaches a WeBWorK server
  through a proxy; whether the `/generate` queue has the same access is not known
  (it runs with no network for Asymptote and Sage).
- **The publication catalog has no WeBWorK or STACK settings**
  (`app/models/publication/catalog.rb`).

## Phase 1 — iframe pages in pretext-html — done, released in 0.20.0

- Both preview wrappers carry a copy of upstream's `create-iframe-page` with the
  `exsl:document` swapped for an inert `<template data-ptx-iframe-page="NAME">`,
  generated by `refresh-xsl.mjs` (which fails if upstream changes the template's shape).
- The renderer lifts those out and returns `RenderResult.iframePages`, a map from
  filename (`<id>-if.html`) to a complete HTML document. The iframes in `html` are left
  as PreTeXt emits them.
- `embedIframePages(html, pages, { sandbox })` inlines each page as its iframe's
  `srcdoc`; also exported from the `./iframe-pages` subpath, which does not import the
  WASM renderer. The editor does not use it (see Phase 2) but the CLI does.

## Phase 2 — deliver the pages in LivePreview — done

`packages/web-editor/src/components/iframePages.ts`, wired into `LivePreview.tsx`.

- `iframePages` rides along on `PreviewRender`, through the worker and the inline path.
- On the HTML string, before delivery (`markIframePages`): an iframe naming a page loses
  its `src`, so nothing requests a file that does not exist, and gains
  `data-ptx-iframe-page` and `sandbox="allow-scripts"`. The page text stays out of the
  HTML, so the live patcher sees an unchanged iframe and leaves it running.
- On the live DOM, after each load or patch (`deliverIframePages`): each marked iframe
  gets its page as `srcdoc`, only when the text differs from what that element last got.
- Each page gets a `<base href>` to the editor's page and the same `generated/…`
  rewriting as the main page (`prepareIframePages`).

Checked in the real editor (headless Chromium, `/tryit`):

- An author's `<script>` in a `platform="javascript"` interactive runs and draws, from
  origin `null`: reading `document.cookie`, `parent.document` and `localStorage` all
  throw.
- Editing a paragraph beside the interactives reloads none of them. Editing one
  interactive's script reloads that one and not its neighbour.
- Desmos and a YouTube embed load. YouTube showed its player, not the no-referrer
  refusal.

**GeoGebra does not run in the sandbox.** Its loader (GWT) writes into a child frame's
document, which an opaque origin may not do; the applet stays on its loading picture.
So a page that is nothing but one GeoGebra material — what `<interactive geogebra="ID"/>`
makes — is framed from `https://www.geogebra.org/material/iframe/id/ID` instead
(`geogebraMaterialUrl`), which was seen drawing the applet. That URL answers with status
410 and a working page, so it logs one failed request; if GeoGebra ever makes the 410
real, this stops working and the sandboxed page is all that is left.

Not done, and why:

- **GeoGebra with more than a material** (a local `.ggb`, an `appletOnLoad` script, more
  than one applet) keeps its sandboxed page and does not load. It needs pages served
  from a separate origin; that is infrastructure, and is now an open question below.
- **JSXGraph, D3, Sage and DoenetML were not watched.** PreTeXt takes a JSXGraph or D3
  script only from `@source`, a file, which needs Phase 3. Whether Sage cells and
  DoenetML survive an opaque origin is unknown.
- **The server-rendered fallback (no JSPI)** was not exercised. It posts to the build
  server, which builds real pages; nothing in this phase touches that path.
- The "open in new tab" link under an interactive needed nothing: the renderer already
  emits it with no `href`, as it does every link that leaves the page.

## Phase 3 — file assets that are not images — deferred

**Decided 2026-11-11: not now.** Only externally hosted interactives are supported for
the time being — the kinds another site serves (Desmos, GeoGebra materials, CalcPlot3D,
YouTube, a framed page, MyOpenMath). No new file types are accepted, and multi-file
applets are out of scope. Interactives an author writes themselves are expected to
arrive later as authored assets, in an explorer tab of their own beside images,
snippets and exercises, rather than as uploaded files; the steps below are kept as
notes for that design, not as a plan of record.

Until then, everything that needs a local file stays unavailable in the editor:
JSXGraph and D3 (PreTeXt takes their scripts only from `@source`), a GeoGebra `.ggb`,
`interactive @iframe="local.html"`, `video @source`, and STACK's question file.

1. Teach `Content::AttachedFiles` the types interactives need, each with an extension:
   `.js`, `.css`, `.ggb`, `.html`, `.mp4`, `.webm`, `.vtt`, and STACK's `.xml`.
2. Decide how each is served. Media can be inline. JavaScript and HTML must be inline to
   work, and must not be inline on the app's origin: serve them from the CDN or
   `pub`-style origin, or only ever into sandboxed frames.
3. Asset list and settings drawer: a sensible row for a non-image (no thumbnail, the
   extension shown), and upload accepting these types.
4. Decide about multi-file local applets (an HTML file with its own scripts in a
   folder). Flat refs that reference each other may be enough; folders are a larger
   change to the `external/:ref` route and the archive.

## Phase 4 — authoring

1. **Done.** Insert → "Interactives & Media": Desmos, GeoGebra, CalcPlot3D (always
   writing `@variant`), YouTube and a generic iframe ("Web Page"). MyOpenMath and
   WeBWorK problems are exercises, so they sit under "Interactive Exercises" — the
   WeBWorK one an Open Problem Library problem by `@source`, external like
   MyOpenMath's, and offered ahead of any preview of it, its description saying so. PreTeXt
   only, unless the LaTeX and Markdown converters gain a spelling. Every body passes the
   schema in `__tests__/snippets.test.ts`. Seen in the editor: the menu, and the
   CalcPlot3D default drawing its surface.
2. **Done.** A paste that is nothing but a link to a Desmos graph, a GeoGebra material
   or a YouTube video arrives as the element, id extracted (and a YouTube `t=` as
   `@start`): `mediaUrls.ts`, called from `pasteConvert.ts`. Not an offer but the
   convention LaTeX pastes already follow — converted where a block belongs, left as a
   link inside a paragraph, off with the Edit menu's paste toggle, and Ctrl+Shift+V
   pastes the link itself. The element carries no `xml:id`, which could collide.
   Desmos's 3D calculator and YouTube playlists are left as links: `@desmos` frames
   only `/calculator/`.
3. **Done.** `editorConfigs/interactiveDiagnostics.ts`: a warning, with a quick fix, on
   `@calcplot3d` without `@variant`; and a note on an interactive with neither
   `@preview` nor a `<static>`, only when the project has a target that is not a web
   page (`Target::Catalog.static_slugs`, passed to the editor as `hasStaticOutput`).
   Seen in the editor: the warning, and the paste both ways. The static note was only
   unit-tested, since no development project has a PDF target.

## Phase 5 — external exercises

- **MyOpenMath: done.** The Insert entry is in (Phase 4), and a problem was seen in the
  live preview: the question drawn, with its answer box and Submit button, the frame
  sized to it.
- **STACK:** waits on Phase 3 for its question file. `stack-server` in the publication catalog; confirm upstream's `stack-js`
  reaches the single-page preview; the question file comes from Phase 3.
- **WeBWorK**, in three steps:
  1. The server setting in the publication catalog, and one real build of a WeBWorK
     problem through the build server's proxy.
  2. In the preview, replace the error with a placeholder ("WeBWorK problem — rendered
     in full builds") around the authored statement, and make a `@source`-only problem
     say what it is instead of rendering empty. **This belongs in pretext-html's preview
     stylesheets (pretext-tools), like Phase 1**: the page the renderer returns has
     nothing marking a WeBWorK problem to rewrite here. Measured on 0.20.0: an authored
     problem shows its `pg-code` as loose text above a statement whose math still holds
     the Perl variables (`$a + $b`), and a `@source`-only one is an empty box.
  3. Live preview: have `/generate` produce the representation files
     (`generated/webwork/<id>.xml`) and hand them to the renderer through its virtual
     mount — assembly loads them with `document()`, which the fetch shim serves. Depends
     on `/generate` reaching the WeBWorK proxy.

## Phase 6 — static outputs

PDF and EPUB need a `@preview` image per interactive, YouTube thumbnails, and QR codes.
PreTeXt makes them with Playwright and the network (`pretext generate interactive
youtube qrcode`). Find out what the build server does for these today, and whether the
build queue (not `/generate`) is where they belong.

## Upstream

Worth proposing to PreTeXt: emit `@platform` pages as `srcdoc`, or put the
`exsl:document` in a template of its own so a wrapper can replace it without copying
the page. Either shrinks Phase 1 to a few lines. Nothing here waits on it.

## Open questions

- Does `/generate` reach the WeBWorK proxy the build queue uses?
- A separate origin for iframe pages, so GeoGebra beyond a bare material (and whatever
  else turns out to need same-origin access to its own frames) can run with
  `allow-same-origin` and still reach nothing of the app's. Could be the `pub`-style
  origin of `docs/build-targets.md`.
- Do Sage cells and DoenetML survive `sandbox="allow-scripts"`? JavaScript does;
  GeoGebra does not.
- Do the interactives' iframes resolve in the server-rendered fallback preview?
